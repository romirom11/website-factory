Єдиний зведений документ для Романа: що це, як підняти, що зробити руками, щоб
перейти в live. Деталі кожної підсистеми — у `docs/` (посилання по тексту).
Авторитет при конфліктах — `docs/SPEC.md`.

## (а) Що це і з чого складається

Автономна фабрика: знаходить локальні бізнеси в Google Maps → збирає **evidence
package** (кожен факт має source → immutable raw-обʼєкт) → будує
персоналізований демосайт → показує тобі картку на approve → і **лише після
твого approve** відправляє повідомлення. Оркеструє детермінований код: Postgres
— state machine і джерело істини, pg-boss — черга, агенти — воркери лише для
нечітких етапів. LLM ніколи не вирішує переходи статусів.

| Сервіс | Порт (127.0.0.1) | Роль |
|---|---|---|
| `postgres` | 5432 | стан, черга (pg-boss), історія статусів |
| `minio` | 9000 / 9001 | object storage: raw evidence, скриншоти, QA-звіти |
| `gosom` | 8085 | google-maps-scraper, REST API — **єдине** джерело discovery |
| `factory` | 8787, 8788 | воркери `core,enrich` + JSON API/вебхуки (8787) + сервер демо (8788) |
| `factory-build` | 7681 | воркери `build` (brief → збірка → visual QA), окремий семафор; на 7681 — **живий термінал збірки**, до якого можна підключитись |
| `ui` | 3000 | **контрольний інтерфейс**: approve-черга, воронка, кампанії, jobs, розмови |
| `waha` | 3001 | self-hosted WhatsApp HTTP API (НЕ Meta Cloud API) |
| `greenmail` | 3025/3143/8081 | лише dev (`--profile dev-mail`): локальні SMTP+IMAP для тестів |

`factory` і `factory-build` — один образ, різні `WORKER_GROUPS`. Розділені
навмисно: семафор агентів діє **на процес**, тож 40-хвилинна збірка сайту і
беклог enrichment інакше голодують один одного.

**Інтерфейс — це UI на :3000.** Telegram лише надсилає посилання в UI, approve
там не робиться (рішення №9). `:8787` — службовий API, не інтерфейс.

## (б) Локальний запуск (dev)

```bash
cp .env.example .env
cp -r skills/* .claude/skills/          # skills/ — джерело правди

# Обовʼязкове в .env (решта налаштувань — в UI /settings, див. чекліст (г)):
echo "UI_PASSWORD=$(openssl rand -hex 16)" >> .env
echo "SETTINGS_MASTER_KEY=$(openssl rand -hex 32)" >> .env

docker compose up -d postgres minio gosom
pnpm install && pnpm db:migrate

pnpm typecheck && pnpm tsx scripts/smoke.ts    # обидва мають бути зелені
pnpm tsx scripts/test-settings.ts              # шифрування + порядок БД→env→дефолт
pnpm tsx scripts/test-accounts-parse.ts     # парсинг PTY-виводу claude setup-token / codex login
pnpm all                                        # воркери + API :8787 + демо :8788
pnpm ui:dev                                     # UI :3000 (в іншому терміналі)
```

Мінімум для UI — `UI_PASSWORD` у `.env`, інакше контейнер `ui` **відмовиться
стартувати** (це навмисно: інтерфейс без автентифікації не піднімається).
`SETTINGS_MASTER_KEY` потрібен, щоб зберігати секрети — без нього сторінка
налаштувань покаже, як його згенерувати, і не дасть зберегти жоден токен.

Уже маєш робочий `.env` зі старим набором змінних? Перенеси їх у зашифроване
сховище одним проходом (ідемпотентно, `.env` не чіпає):

```bash
pnpm tsx scripts/migrate-env-to-settings.ts --dry   # показати план
pnpm tsx scripts/migrate-env-to-settings.ts         # перенести
```

Локальна пошта без секретів Gmail:

```bash
pnpm phasee:mail                  # greenmail
pnpm tsx scripts/phaseE-e2e.ts    # весь цикл send → лист → reply → follow-up
```

## (в) Продакшн на твоєму хості

```bash
git clone <repo> && cd websites-factory
cp .env.example .env        # ТІЛЬКИ інфраструктура — див. крок 0 чекліста (г)
docker compose up -d        # greenmail не підніметься: він за профілем dev-mail
docker compose logs -f factory

open http://<host>:3000/settings   # решта конфігурації — тут, у браузері
```

Міграції застосовуються **автоматично** при старті контейнерів (`db:migrate` у
CMD обох factory-сервісів, ідемпотентно).

Після першого запуску конфігурація живе в БД, тому подальші зміни (новий токен,
інший ліміт, dry_run↔live) **не потребують ані редагування файлів на сервері,
ані `docker compose up`** — тільки сторінку `/settings`.

**Бекапити треба volume-и:**

| Volume | Що всередині | Втрата = |
|---|---|---|
| `pgdata` | вся БД: бізнеси, evidence-звʼязки, approvals, черга | все |
| `miniodata` | raw evidence, скриншоти, QA-звіти | докази під фактами |
| `wahasessions` | сесія WhatsApp | новий QR-скан |
| `codexhome` | логін Codex CLI | новий `codex login` |
| `.env` (файл, не volume) | `SETTINGS_MASTER_KEY` | **усі збережені секрети стають нечитабельними** — доведеться ввести заново в `/settings` |
| томи `deploysdata`, `sitesdata` | задеплоєні демо і воркспейси збірок | демо (перебудовуються); глянути з хоста: `docker compose cp factory:/app/deploys ./` |

**Всі порти привʼязані до `127.0.0.1`** — навмисно. Назовні виставляй **лише**
через Tailscale або reverse-proxy з автентифікацією і TLS. Що категорично не
можна відкривати в інтернет: `waha` (сесія WhatsApp = креденшел, відкритий WAHA
= захоплення акаунта), `minio`, `postgres`, **`7681` (термінал збірки — це жива
сесія агента в контейнері)**. Якщо UI стає публічним — постав
`UI_BASE_URL` (у `/settings` → **Система**) на публічний URL: Telegram-лінки
беруться саме звідти.

### Термінал збірки — щоб кнопка «Відкрити термінал» працювала

Збірки за замовчуванням ідуть у tmux, щоб до них можна було підключитись і
бачити справжній термінал агента, а не лише переказ подій. Образ уже містить
`tmux` і `ttyd`; на сервері лишається **одне** — сказати UI, за якою адресою той
термінал доступний ТВОЄМУ браузеру:

```bash
# у .env, або одразу в /settings → Агенти → «Адреса термінала збірки»
BUILD_TERMINAL_BASE_URL=http://<host-або-tailscale-імʼя>:7681
```

Порт `7681` опублікований на `127.0.0.1` контейнера `agent-runner-executor`, тому
«з браузера» означає: через Tailscale, SSH-тунель (`ssh -L 7681:localhost:7681
<host>`) або той самий authenticated reverse-proxy, що й UI.

**Як це налаштовано на бойовому сервері (2026-08-22):** Dokploy сам не вміє
додати path-маршрут на compose-сервіс, тому маршрут заведений РУЧНИМ файлом
`/etc/dokploy/traefik/dynamic/website-factory-terminal-custom.yml` —
`Host(website-factory.kdnx.cloud) && PathPrefix(/terminal)` →
`http://agent-runner-executor:7681`, priority 100 (вище за Host-only роутер UI).
Traefik підхоплює зміни файлу без рестарту; Dokploy цей файл не генерує і не
чіпає. При переїзді сервера файл треба перенести або створити заново, а в
«Адресі термінала збірки» стоїть `https://website-factory.kdnx.cloud/terminal`.
Памʼятай: ttyd живе лише під час активної збірки — поза нею `/terminal`
відповідає 502/504, і це норма, а не зламаний маршрут. Пароль — basic auth,
логін `roman`, пароль **похідний** від приватного `RUNNER_EXECUTOR_API_KEY`;
побачити його можна
так:

```bash
docker compose exec agent-runner-executor node -e "console.log(require('crypto').createHash('sha256').update('build-terminal:'+process.env.INTERNAL_API_KEY).digest('hex').slice(0,24))"
```

Якщо `BUILD_TERMINAL_BASE_URL` порожній — нічого не ламається: у картці бізнесу
замість кнопки зʼявиться підказка, як підключитись по SSH
(`docker compose exec agent-runner-executor tmux attach -r -t build-<requestId>`).

Термін «підключитись» тут означає **дивитись**. Щоб мати змогу друкувати живому
агенту, треба свідомо ввімкнути `BUILD_TERMINAL_WRITABLE` (у `/settings` →
Агенти, розділ «показати всі параметри»). Типово вимкнено, і це не перестраховка:
натиснута в терміналі клавіша змінює демо клієнта без approval і без сліду в
історії, тоді як кожна інша зміна у фабриці має і те, і те.

Якщо на хості раптом немає tmux — збірки не падають: рантайм сам переходить на
безголову SDK-сесію і пише про це у лог. Термінала в такому разі просто немає.

## (г) Чекліст одноразових дій Романа для переходу в live

> **Головне, що змінилося (рішення Романа, 2026-08-17):** усе нижче, крім
> кроків 0 і 8, робиться **в браузері на `/settings`**, а не редагуванням
> `.env`. Збережене діє **наживо** — фабрика перечитує налаштування протягом
> ~15 секунд, без `docker compose restart` і без ребілду. Секрети лежать у
> Postgres зашифровані (AES-256-GCM) під `SETTINGS_MASTER_KEY`.
>
> **Оновлення (2026-08-17, друге):** підключення акаунтів — це вже не поля з
> токенами, а розділ **«Акаунти»** на `/settings` (сторінка розбита на розділи
> з бічним меню) з кнопкою **Підключити** в кожному рядку. Термінал більше не
> потрібен для Claude або Codex: UI просить runner executor запустити
> `claude setup-token` / `codex login`, показує посилання (і код, де він
> потрібен) та зберігає credential у його окремому volume. OpenCode поки має
> власний інтерактивний TUI, тому логіниться командою
> `docker compose exec agent-runner-executor opencode auth login`.
>
> Коротка версія всього кроку (г): **відкрий `/settings` → «Акаунти», клікни
> рядок і натисни «Підключити».** Розгорнуті пояснення нижче — на випадок,
> коли щось відповіло помилкою.
>
> Порядок розвʼязання значення: **БД (UI) → env → дефолт**. Тобто змінна в
> `.env` лишається робочим fallback-ом для свіжої машини чи відкату, але щойно
> ключ збережено в UI — виграє БД.
>
> Біля кожного поля видно, звідки взялося значення (`БД` / `env` / `дефолт`),
> хто і коли його змінив.

### 0. `.env` — шість локальних секретів (єдиний крок у файлі)

```bash
cp .env.example .env
echo "UI_PASSWORD=$(openssl rand -hex 16)" >> .env          # вхід у консоль
echo "UI_SESSION_SECRET=$(openssl rand -hex 32)" >> .env    # підпис cookie
echo "SETTINGS_MASTER_KEY=$(openssl rand -hex 32)" >> .env  # ключ шифрування секретів
echo "INTERNAL_API_KEY=$(openssl rand -hex 32)" >> .env     # UI → фабрика (кнопки «Перевірити»)
echo "RUNNER_API_KEY=$(openssl rand -hex 32)" >> .env       # фабрика → runner gateway
echo "RUNNER_EXECUTOR_API_KEY=$(openssl rand -hex 32)" >> .env # gateway → executor
```

Плюс `DATABASE_URL` / `POSTGRES_PASSWORD` / `S3_*`, які вже є в шаблоні.

**`SETTINGS_MASTER_KEY` бекап обовʼязковий** — разом із паролем БД. Після його
зміни всі збережені секрети стають нечитабельними, і їх треба ввести заново
(код у цьому випадку деградує до «не налаштовано», не крешить).

```bash
docker compose up -d
open http://localhost:3000/settings      # далі — тільки тут
```

Перед підключенням акаунтів перевір production boundary один раз після кожної
зміни `Dockerfile.runner`, Compose networks або egress allowlist:

```bash
docker compose build agent-runner-gateway agent-runner-executor agent-egress-proxy agent-egress-dns
pnpm test:runner-isolation
```

Тест підіймає окремий тимчасовий Compose project і перевіряє: approved npm
через proxy; deny для arbitrary CONNECT, direct fetch, Python urllib, raw IP і
DNS; відсутність route до Postgres/MinIO/factory/host; exact-workspace write;
deny для сусіднього workspace, auth volumes і parent `/proc`; read-only root,
mount/network/capability topology та fail-closed readiness. Після себе він
видаляє тільки власні test volumes/networks.

Allowlist не розширюється лише в одному місці. Для нового provider/package
domain онови `infra/agent-proxy/squid.conf`, `infra/agent-dns/Corefile` і, якщо
домен потрібен tool subprocess Claude, `APPROVED_TOOL_DOMAINS` у
`src/agents/confinement.ts`; потім перебудуй образи й обов'язково повтори тест.
OpenCode дозволений у production лише для tool-free structured stages; для
builder/QA-fix обери Claude Code або Codex.

### 1. Claude Code по підписці (без цього агентні етапи не працюють)

`/settings` → **Підключені акаунти** → рядок **Claude Code** → **«Підключити»**.

Далі все на сторінці:

1. runner executor запускає `claude setup-token` і показує
   **посилання** — відкрий його (кнопка відкриває нову вкладку; поруч є те саме
   посилання текстом, якщо треба відкрити на іншій машині);
2. увійди акаунтом з підпискою **Pro/Max** і скопіюй код, який покаже сторінка;
3. встав його в поле **«Вставте код зі сторінки»** → **«Надіслати код»**;
4. токен записується з правами `0600` у credential volume executor-а, і runner одразу робить
   **справжній агентний виклик** для перевірки. Зелений рядок = працює.

На все відведено 5 хвилин, далі сесія сама згасає (кнопка «Скасувати» — будь-коли).
Помилки приходять словами самого CLI:

- `Claude відхилив код: Invalid code…` — код скопійований не повністю; тисни
  «Підключити» ще раз і скопіюй цілком (кожен запуск дає нове посилання);
- `Токен збережено, але перевірка не пройшла…` — токен прийнявся, але виклик не
  пройшов; дивись текст перевірки (найчастіше вичерпано ліміт підписки).

**«Відключити»** прибирає credential з runner volume. Legacy-токен із БД можна
одноразово перенести через `RUNNER_SEED_CLAUDE_CREDENTIAL=true`, перевірити й
одразу повернути цей прапорець у `false`.

Жодного `ANTHROPIC_API_KEY` — він не потрібен і свідомо не читається кодом
(рішення №10); більше того, він **прибирається** з оточення процесу логіну, щоб
випадковий ключ у середовищі не перевів білінг на pay-per-token. Без токена
агентні джоби чесно падають у `needs_human`, а не крешать; решта пайплайну
працює.

> Для довідки: `claude setup-token` не має неінтерактивного режиму і взагалі
> нічого не друкує в pipe — фабрика запускає його під псевдотерміналом і читає
> посилання з escape-послідовності, тому це і вдалося сховати за одну кнопку.

### 2. Codex CLI (для gen-image)

`/settings` → **Підключені акаунти** → рядок **Codex CLI** → **«Підключити»**.

Сторінка покаже посилання (`auth.openai.com/codex/device`) і **одноразовий код**
на кшталт `XD37-SXIBN`. Відкрий посилання, увійди акаунтом з підпискою ChatGPT,
введи код **там**. Сюди його повертати не треба: CLI сам опитує OpenAI, і щойно
ти підтвердиш — рядок стане зеленим.

Логін лягає у volume `codexhome` і **переживає ребілди образу**, тож це справді
одноразова дія. Кнопка **«Перевірити»** будь-коли показує `codex login status`.

Відключення з браузера навмисно немає: це твоя ChatGPT-сесія на диску, і
прибирається вона однією командою — `docker compose exec agent-runner-executor codex logout`.

### 3. Telegram (сповіщення + лінки в UI)

`/settings` → **Підключені акаунти** → рядок **Telegram**.

1. BotFather → `/newbot` → скопіюй токен → встав у поле → **«Зберегти токен»**.
2. **Напиши боту будь-яке повідомлення** в Telegram (без цього `getUpdates`
   не має що показати — це обмеження Telegram, не наше).
3. **«Знайти chat id»** → сторінка покаже список чатів, які писали боту →
   **клікни свій**. Chat id збережеться, і одразу піде **тестове повідомлення**.

Прийшло в чат = канал працює. Помилка приходить словами самого Telegram
(`Unauthorized` для битого токена, `chat not found` для чужого id).
Кнопка **«Надіслати тест»** повторює перевірку будь-коли.

Без цього все працює, сповіщення просто пишуться в лог.

### 4. Gmail (email-канал і детект відповідей)

`/settings` → **Підключені акаунти** → рядок **Gmail**. Інструкція продубльована
прямо в блоці:

1. Увімкни двофакторну автентифікацію (без неї app password недоступний).
2. https://myaccount.google.com/apppasswords → пароль «websites-factory».
3. Gmail → Settings → Forwarding and POP/IMAP → **Enable IMAP**.
4. Впиши **адресу** і **app password** → **«Підключити»**.

Одна кнопка заповнює обидва блоки (SMTP `smtp.gmail.com:587` + IMAP
`imap.gmail.com:993`), бо в Gmail це один і той самий app password, і одразу
проганяє **обидві** перевірки: `verify()` на живому SMTP-зʼєднанні і реальний
вхід в IMAP із підрахунком листів. Пробіли в паролі можна лишати — Google
показує його групами по чотири, вони прибираються автоматично; якщо символів не
16, форма скаже про це замість того, щоб мовчки зберегти не те.

Далі — у «Розширених», якщо треба тонше:

- `SMTP_MESSAGE_ID_DOMAIN` **не міняй після старту розсилки** — у Message-ID
  закодований idempotency key, по ньому матчаться відповіді.
- `OUTREACH_DAILY_LIMIT` тримай ≤ 20–30 (ліміт Gmail ~500, але репутація
  псується задовго до нього).

Застереження зі спеки (§2.2, рішення #1): якщо Gmail почне флагати листи —
переїзд на окремий домен переглядається першим.

### 5. WhatsApp через WAHA — QR прямо в UI

**Візьми ОКРЕМИЙ номер.** Не свій особистий: протокол неофіційний, при розсилці
на незнайомі номери WhatsApp банить.

Сам контейнер WAHA читає свої секрети з `.env` (це його власний конфіг, не наш
settings-стор), тому спершу:

```bash
echo "WAHA_API_KEY=$(openssl rand -hex 32)" >> .env
echo "WAHA_HOOK_HMAC_KEY=$(openssl rand -hex 32)" >> .env
echo "WAHA_DASHBOARD_PASSWORD=$(openssl rand -hex 16)" >> .env
# і ПРИБЕРИ WAHA_ALLOW_DEV_KEY=true — це лише для локального dev
docker compose up -d waha
```

Той самий `WAHA_API_KEY` і HMAC key впиши в `/settings` → **Outreach** →
«Показати всі параметри» → поля WAHA → Зберегти. Далі — **Акаунти** → рядок
**WhatsApp** → **«Перевірити / показати стан»**:

- `WORKING` — номер уже привʼязаний, нічого робити не треба;
- `SCAN_QR_CODE` — QR зʼявиться **прямо в цьому рядку** (кнопка «Оновити QR» —
  він живе ~20 секунд). Скануй телефоном з номером розсилки: WhatsApp →
  Пристрої → Привʼязати пристрій;
- `FAILED` / немає сесії — перезапусти сесію і тисни «Оновити QR».

Дашборд WAHA на окремому порту з окремим паролем не потрібен.
Фабрика відмовляється відправляти, поки статус не `WORKING`. Тримай телефон
онлайн (WhatsApp Web — дзеркало телефона).

### 6. Відео для hero — авто + ручний wow-кліп

FlowKit видалено (SPEC §2.5, 2026-08-22): будь-який міст до Google Flow вимагає
живого залогіненого Chrome поза датацентром, а на маку нічого не живе.

Нічого налаштовувати не треба:

- **Авто**: кожна збірка сама робить Ken-Burns-кліп з реального hero-фото через
  ffmpeg (є в образі). Якщо ffmpeg недоступний — CSS/GSAP Ken Burns у браузері.
- **Wow-відео**: на картці бізнесу (вкладка **Демо**) є блок «Відео для hero» —
  промпт пише арт-директор під обраний дизайн (з'являється після першої
  збірки) + стартовий кадр. Згенеруй у будь-якому
  інструменті, завантаж mp4 тією ж карткою — наступна збірка чи «Ще спроба»
  використає його замість Ken Burns автоматично. Файл позначається
  `ai_generated` / `private_demo_only` і ніколи не видається за реальне відео.

### 7. Перемикач у live

`/settings` → блок **«Режим фабрики»** вгорі сторінки → «Перемкнути в live».
Потрібно вписати слово `live` для підтвердження: в цьому режимі кожен approve
надсилає **реальне повідомлення реальному бізнесу**, і відкликати його
неможливо. Повернення в `dry_run` — одна кнопка без підтвердження.

До цього моменту весь флоу вже працює, але send **симулюється** (`simulated`).

Там же поруч: `OUTREACH_DAILY_LIMIT` і `FOLLOWUP_SCHEDULE_DAYS`.

### 8. Хостинг: arm64 vs amd64

- `gosom/google-maps-scraper` — образ **amd64**; на Apple Silicon іде через
  емуляцію (повільно, але працює). На звичайному Linux-сервері — нативно.
- WAHA на arm64 потребує `WAHA_IMAGE=devlikeapro/waha:noweb-arm`; на amd64
  дефолтний `devlikeapro/waha:noweb`.

### Панель «Стан системи»

Вгорі `/settings`, під режимом фабрики: Postgres, MinIO, gosom, Factory API,
WAHA — живі проби; **heartbeat воркерів** (кожен процес фабрики штампує рядок
раз на 30 секунд, тому «застій» = воркери зависли, навіть якщо контейнер
формально піднятий); глибина черги pg-boss.

Внизу сторінки — **«Що бачить фабрика зараз»**: питає живий процес `factory`,
яку конфігурацію він реально використовує. Це і є відповідь на «я змінив
значення — воно доїхало?» без читання логів.

## (д) Як запустити кампанію

1. UI → **Кампанії** → створити (країна, місто, ніша, мова, запити, target,
   **політика збірки** — див. нижче).
2. Запустити — або з UI, або `pnpm factory campaign:run --id <id>`.
3. Спостерігати: **Воронка** (розподіл по статусах), **Jobs** (черга і падіння),
   **Approve-черга** (готові демо).
4. На кожне готове демо приходить Telegram-лінк → відкриваєш картку в UI →
   дивишся демо в iframe → **Approve / Reject / Changes**.
5. Після Approve повідомлення відправляється **рівно один раз**. Ручні канали
   (Instagram) дають deep-link кнопку: відкрив, вставив, відправив, підтвердив.

### Політика збірки: кому фабрика сама будує демо

`production_ready` означає «доказів вистачає, щоб зібрати чесне демо». Це **не**
означає «збирай». Кому саме фабрика витрачає години підписки — вирішує
`campaigns.auto_build` (поле в формі створення і редаговане в таблиці кампаній):

| Політика | Кого фабрика будує сама |
|---|---|
| `no_site_only` (типово) | лише тих, у кого останній вердикт аудиту `no_website` або `broken` |
| `all` | кожного, хто дійшов до `production_ready` |
| `manual` | нікого — тільки кнопкою в UI |

**Бізнес без аудиту не збирається при `no_site_only`**: «ми не дивились» — це не
доказ «сайту немає», і збірка на здогад не запускається. Такий бізнес спокійно
чекає в `production_ready` — це нормальний стан спокою, а не залипання.

Порядок у черзі збірок — пріоритет pg-boss: `no_website` > `broken` > решта,
і вже всередині тира — за score. Тобто слабкий лід зовсім без
сайту збирається раніше за сильний лід із робочим сайтом.

### Як вибрати бізнеси руками

**Воронка** відкривається одразу на робочому списку: `production_ready` без
власного сайту, найкращий score зверху. Далі:

- фільтри: кампанія, статус (мульти), вердикт аудиту (мульти + чіп **«Без
  сайту»**), наявність Instagram / WhatsApp / email, `score ≥ N`, пошук;
- сортування: score, відгуки, рейтинг, оновлено, назва;
- усе живе в URL — вигляд можна переслати собі й відкрити з телефона;
- **«Будувати демо»** на рядку або масово над відфільтрованим списком. Один
  бізнес — одна збірка: якщо `site_project` уже в роботі або job у черзі, кнопка
  вимкнена з поясненням;
- `needs_review` збирається лише коли **немає відкритих hard-gaps** (інакше кнопка
  вимкнена і в тултипі перелічені gaps). При підтвердженні бізнес спершу
  переводиться в `production_ready` з actor `roman` — це лягає в `status_history`.

**Таймінги, чого очікувати** (виміряно на реальному прогоні):

| Етап | Час |
|---|---|
| discovery (1 запит, depth 1) | ~8 хв (arm64 через емуляцію) |
| enrich одного бізнесу | 1–3 хв |
| збірка сайту (`build-site`) | 20–40+ хв, буває довше |
| visual QA ітерація | 3–8 хв, до 3 ітерацій |

**Ліміти підписки — це не помилка.** При вичерпаному вікні job переходить у
`retry_wait` з `next_attempt_at`, лічильник спроб не витрачається, job
перезапускається з тим самим idempotency key. У `failed` через ліміт не
потрапляє ніколи.

## (е) Відомі обмеження і TODO

**Дизайн (головне; `docs/BUILD-PIPELINE.md` §12).** Перше демо ти відхилив як
візуально слабке. Детерміновані гейти вже додані (обрізаний текст, щільність
контенту `inkPer1000px`, плейсхолдери). **Чекає спільного проходу з тобою:**
підкладати критику PNG референсу для прямого порівняння; осі «density» і «wow»
в рубриці; вимога, щоб ≥3 компоненти пулу реально анімувались у DOM; гейт на
частку площі під медіа; поріг «висота сторінки vs обсяг тексту». Пороги
відкалібровані **на двох сторінках** — перекалібрувати на 5–10 реальних демо.

**Outreach.**
- Живу відправку WhatsApp **не перевірено** (немає окремого номера і QR-скану);
  перевірені webhook, HMAC, `check-exists`, гейти. Email-цикл перевірено
  повністю на GreenMail, включно з reply і bounce.
- Анти-спам таймлок WhatsApp не опрацьовано: при масовій розсилці на незнайомі
  номери банять. Тому окремий номер і малі денні ліміти.
- Instagram DM не автоматизується принципово (бан акаунта) — фабрика готує
  текст і дає deep link.

**Discovery.** gosom обробляє **одну job за раз**; кампанії з багатьма запитами
йдуть послідовно. Проксі закладені конфігом (`GOSOM_PROXIES`, типово порожньо).

**Пошук соцмереж.** Крок працює **без ключів** — через публічну видачу
пошуковиків у Playwright (Brave → Startpage → Bing → DuckDuckGo), тому впирається
в їхні ліміти:

- Brave віддає **429** після кількох запитів з однієї IP; DuckDuckGo
  (`html.` / `lite.`) з домашньої IP віддає **403** практично завжди. Тому
  двигунів чотири і той, що відмовив, вимикається до кінця прогону.
- Instagram і Facebook показують **login wall**. Публічного `og:title` /
  `og:description` вистачає (саме там біо з телефоном і адресою), але біо
  довші за ~150 символів обрізаються, і закритий профіль не дасть нічого —
  такий кандидат чесно лишається `medium`/`weak`, а не «верифікується».
- Невдача пошуку **ніколи** не валить збагачення: це warning + gap
  `socials_unresolved`.
- Якщо ліміти почнуть заважати на великих кампаніях — збільшити
  `SOCIAL_DISCOVERY_DELAY_MS` (типово 2500 мс) або пустити крок через проксі.
  Вимикається повністю: `SOCIAL_DISCOVERY=false`.

**Збірка.** Workspace однієї збірки ~735 МБ; після термінального стану GC
чистить до ~9 МБ (`WORKSPACE_GC=false` вимикає). Референси є **лише для ніші
beauty** — нова ніша потребує своєї теки `references/<niche>/`.

**Термінал збірки (`BUILDER_MODE=tmux`).** Що перевірено і що ні:

- Перевірено офлайн (`pnpm test:tmux-agent`, 35 перевірок): гард CLI-хука
  збігається з SDK-гардом на всіх кейсах (вихід за workspace, `~/.ssh`, `.env`,
  `curl` назовні vs loopback, `WebFetch`), хук fail-closed на битому payload,
  ttyd-argv справді read-only і з basic auth, маркер живої сесії протухає.
- **Не перевірено живим прогоном**: справжня сесія `claude` у tmux
  (`pnpm test:tmux-agent --live`) і сам `ttyd`. На маку Романа немає ні tmux, ні
  ttyd, а ставити їх на його машину я не став. **Перший крок на сервері:**
  `docker compose exec agent-runner-executor pnpm test:tmux-agent --live` — це підніме
  одну коротку справжню сесію і перевірить весь ланцюг (сесія → промпт-файл →
  `result.json` → скролбек → прибирання). Поки цього не зроблено, тримай
  `BUILDER_MODE=sdk`, якщо не хочеш ризикувати першою реальною збіркою.
- Один attachable terminal на executor через єдиний порт ttyd; headless-виклики
  паралельно використовують окремі ліміти `core` / `enrich` / `build`.
- Якщо `claude` у tmux завершиться, не написавши `result.json`, збірка впаде з
  причиною (`idle` / `gone` / `timeout`) і хвостом pane у тексті помилки; повний
  скролбек лишиться у `sites/<biz>/<projectId>/terminal.log`.

**Медіа.** Hero-відео: авто Ken Burns через ffmpeg (в образі) або завантажений
з картки wow-кліп. Онлайн-генерації відео у фабрики немає — свідомо (SPEC §2.5).

## (ж) Траблшутинг

**`docker compose exec` лається на WAHA-змінні.** Compose інтерполює змінні
ВСІХ сервісів на КОЖНІЙ команді. Тому у WAHA дефолти-заглушки, а захист —
всередині контейнера: він відмовляється стартувати із заглушкою, якщо не
виставлено `WAHA_ALLOW_DEV_KEY=true`.

**`ERR_PNPM_IGNORED_BUILDS` при збірці образу.** pnpm 11 виходить з ненульовим
кодом, якщо build-скрипти залежностей заблоковані. Дозвіл живе **тільки** в
`pnpm-workspace.yaml` (`allowBuilds: { esbuild: true }`). pnpm 11 видалив
`onlyBuiltDependencies`; старе поле лише мовчки залишало нативний setup
заблокованим. Workspace-файл **обовʼязково** копіюється в образ.

**Агентні джоби падають з `--dangerously-skip-permissions cannot be used with
root`.** Claude Code відмовляється працювати під root. Образ тому запускається
під користувачем `node` (uid 1000) — не «хардening», а умова працездатності.
Якщо повернути root, впадуть **усі** агентні етапи навіть з валідним токеном.

**Бізнеси залипли в `site_in_progress`.** Буває, коли `content-and-design` не
міг виконатись (напр. агент не автентифікований). Полагодити:

```bash
pnpm tsx scripts/repair-stuck-site-in-progress.ts           # показати
pnpm tsx scripts/repair-stuck-site-in-progress.ts --apply   # повернути в production_ready
```

Чіпає лише ті, у кого **немає** жодного `site_projects` (тобто збірка навіть не
починалась), і пише кожну зміну в `status_history`.

**Черга засмічена джобами видалених фікстур.**

```bash
pnpm tsx scripts/purge-orphan-jobs.ts           # показати
pnpm tsx scripts/purge-orphan-jobs.ts --apply   # видалити
```

**gosom вічно в `working`.** Тег `v1.14.0` непридатний (тягне драйвер Playwright
з мертвого URL). Закріплено `v1.17.3`.

**Кнопки «Відкрити термінал збірки» немає, хоча збірка йде.** По черзі:

1. `BUILD_TERMINAL_BASE_URL` порожній → кнопки не буде за задумом (у картці
   натомість підказка про SSH). Заповни в `/settings` → Агенти.
2. `BUILDER_MODE=sdk` → термінала немає взагалі, це безголова сесія.
3. tmux не знайшовся в executor → у його логах буде
   `tmux is not installed; falling back to the headless SDK runtime`.
4. ttyd не піднявся → `build terminal not served: …`. Дві типові причини:
   не виставлений `RUNNER_EXECUTOR_API_KEY` (без похідного пароля термінал без
   автентифікації — це шел на хості для будь-кого, тому він свідомо не
   стартує), або порт `7681` уже зайнятий.

**Термінал відкривається, але порожній / «session not found».** Сесія вже
завершилась: ttyd живе рівно стільки, скільки збірка. Те, що встигло
надрукуватись, лежить у `sites/<biz>/<projectId>/terminal.log`.

**Демо відкривається без стилів.** Клас багів з абсолютними шляхами Next-export
під токенізованим URL; вирішено в `serveDir.ts`, health check окремо тягне
stylesheet і вимагає ≥500 байт.
